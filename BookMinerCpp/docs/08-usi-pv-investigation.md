# USI の MultiPV 出力調査

## やねうら王の出力

2026-10-29 に、別リポジトリ `YaneuraOu/source/engine/yaneuraou-engine/yaneuraou-search.cpp`（調査時 HEAD `0f421391`）の `iterative_deepening()`、`SearchManager::pv()`、探索終了時の出力、および `source/usi.cpp` の `on_update_full()` を確認した。

- `SearchManager::pv()` は、設定された MultiPV と合法手数の小さい方まで、順位を 1 から順に出力する。MultiPV 4 の出力中に上位の指し手が変化することは、`multipv 5` が出力されることとは異なる。
- １回の PV 出力でも、更新済み候補は現在の深さの値、未更新候補は前回の深さの値を出す。前回の値が無限値であれば 0 に置き換える。したがって、すべての候補が同じ深さで評価されたとは限らず、順位順のスコアが単調とは限らない。
- `PvInterval` は探索中の出力頻度に影響する。探索停止後にも条件に応じて PV が出力され、探索スレッドや投了判定により最終出力が変わりうる。`lowerbound` / `upperbound` も出力される。詳細は [境界値付き評価値の実験](07-usi-bound-scores.md) を参照。
- `ResignValue` による投了時は、合法手を含む PV の後に `bestmove resign` が返ることがある。bestmove が通常の指し手と一致しないからといって、常に通信異常とは判断できない。

## 実出力の確認

前記の境界値実験のログ（指定評価関数 `evalTuyo12-20261025` の16探索と MaterialLv1 の40探索）を再解析した。MultiPV 1 / 4、`PvInterval` 300 / 0 の探索で、指定された順位を超える `multipv` は現れなかった。これは対象の実装・条件での結果であり、他のエンジンや設定に対する保証ではない。

指定評価関数、MultiPV 4、`PvInterval 0`、初期局面、100,000 ノードの探索では、PV の初手として計7種類が出現した。最後の出力の4手は `7g7f`, `2g2f`, `6i7h`, `6g6f` だった。残りの3手は、それより前の出力で上位4手に入っていた候補であり、`multipv 5` 以降として出力されたものではない。

別途 MaterialLv1、Threads 1、定跡無効、`PvInterval 0` で同じ局面を MultiPV 4・150,000 ノードの後に MultiPV 8・75,000 ノードで再探索した。初期局面では、前者の上位4手は `1g1f`, `5g5f`, `7g7f`, `8g8f`、後者の上位8手は `4g4f`, `2g2f`, `6g6f`, `9g9f`, `1g1f`, `3g3f`, `7g7f`, `4i5h` だった。候補や順位が再探索で変わることを確認できた。この3局面の実験のうち、`7g7f 3c3d` 後の MultiPV 4 の最終出力では2位が -2、3位が 0 だった。

MaterialLv1 に `ResignValue 1` を設定して `7g7f` 後を100,000ノード探索したところ、`info ... score cp -26 upperbound ... pv 1a1b 2g2f` に続いて `bestmove resign` が返った。BookMinerCpp は、このような投了時にも受信済みの合法手の評価値を保持する。

## BookMinerCpp の現状と限界

同じ探索中は順位ごとの最新 PV を保存するため、途中で上位に入っても最終出力で圏外になった指し手は保存されない。MultiPV を増やした再探索では前回の順位表をクリアする。再探索結果が要求数に満たないときは警告し、前回の結果を返すため、その時点で得られた新しい候補も採用されない。この方針が定跡生成に最適かどうかは、この調査だけでは判断できない。

実装は要求した順位を超える `multipv` 行を無視する。これは前述のやねうら王の実験では発生しなかった。他エンジンでの挙動は未検証。実験は少数局面に限られ、より多い局面、スレッド数、エンジンバージョンや特殊局面での挙動を保証しない。

## 詰みと外部定跡の順序

`mate -0` を整数に変換すると符号が消えるため、BookMinerCpp は文字列を先に判定して -32000 として扱う。やねうら王の `USIEngine::value()` には詰まされた側の `mate -0` 出力がある。一方、調査した現行コードの通常の `on_update_full()` は `Score` を使う別経路であり、`Mate` の手数が整数の 0 になると符号を保持できない。実際にどのエンジン・局面で `mate -0` が PV とともに出力されるかは、この調査では確認していない。

外部の DB・YBB の指し手が評価値順とは限らないため、BookMinerCpp は読み込みおよび個別局面の検索時に評価値の降順に整列する。同点の順番は読み込み元の順番を保持する。これにより、ペタショック関連処理が先頭の指し手を最善値として扱う前提を満たす。書き出し時の同点調整とは異なり、並べ替え自体は評価値を変更しない（別途、正規化を指定した場合はその変換が適用される）。
